Before You Write One: Skills Claude Already Has

Authoring a Skill is one of three ways Claude gets a capability. Here are the other two.

Built into every task, zero setup

  • Core tool belt baked into Claude Code: Read, Edit, Write, Bash, Grep, Glob, WebSearch, WebFetch, available with no SKILL.md required.
  • Vision & document understanding: reads screenshots, PDFs, and images directly in context.

Reasoning Claude brings on its own

  • Native reasoning: code generation/debugging, data analysis, summarization, multi-step planning, part of the model itself, not a packaged workflow.
  • Self-orchestration: TodoWrite planning and sub-agent delegation (the Task tool); Claude breaks down its own multi-step work without a Skill telling it how.

Read Stage: Explicit Tool Invocation

Why navigate, not dump?

  • Context bloat: pulling every module and test into context floods Claude's window with noise; signal gets buried
  • Token cost: every unneeded file loaded is spend on text Claude ignores
  • Slower, hedgier answers: Claude qualifies more when context is messy; surgical reads produce sharper responses
  • Transferable habit: Glob → Grep → Read works on any repo, any team, at any scale

The habit

  • Glob the lab folder to confirm fee_rollout.py and test_fee_rollout.py before opening anything else.
  • Grep for quarterly_advisory_fee / monthly_advisory_fee to see both cliff-rate methods side by side.
  • Read the WM-202 ticket (backlog/WM-202-fee-rollout.md) once, for the shared business rule both passes apply.
This lab is one file with two analogous methods, not a folder of tickets; the habit is the same discipline (Glob → Grep → Read) at a smaller scale.

Anatomy of a SKILL.md

Two fields in the frontmatter decide whether Claude Code ever reaches for it.

· · ·

name

The identifier for the Skill, also what you'd type after the / to invoke it directly.

description (with a "USE WHEN" trigger)

What makes auto-discovery work. A vague description is why a technically-available Skill can sit unused; be specific about the situation that should trigger it.

· · ·

Workflow: Ordered list of task descriptions

The body of the Skill: a numbered sequence of steps Claude executes in order. Each step is a plain-language task description, not a script.

Rule of thumb: when to create a Skill.md

"A Skill.md should be created when you are solving the same shape of problem more than once and want to preserve the domain rules so that you don't have to re-explain them each time. This conserves tokens."

Personal vs Project Skills

Same anatomy either way; where the folder lives decides who it follows.

Personal: ~/.claude/skills/<name>/SKILL.md

Lives in your home directory, not the repo. Follows you into every project on this machine; nobody else on the team gets it unless they author their own.

Project: .claude/skills/<name>/SKILL.md

Lives inside the repo, committed like any other source file. Anyone who clones the project gets it, which is what today's fee-rollout Skill should be.

  • A Skill is a folder, not a loose file: <skill-name>/SKILL.md inside one of those two skills/ directories.
  • The folder can also hold a reference.md (loads on demand) or a scripts/ helper, but SKILL.md itself is required.
  • Same-name precedence: enterprise → personal → project.

(c) A "USE WHEN" trigger phrase describing the situation that should invoke it

3. Besides auto-discovery, how else can you run a Skill you've authored?

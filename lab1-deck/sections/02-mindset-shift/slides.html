Meet the Loop: Read → Decide → Act → Observe

Read

Gathers the context it needs: the relevant files, the ticket, the existing tests.

→

Decide

Picks an approach: which files to touch, in what order.

→

Act

Makes the change: edits, runs commands, produces a draft result.

→

Observe

Checks its own result and decides: done, keep going, or stop and ask.

→

Good fit for the loop

A multi-file rename plus a regression sweep: many small Read→Decide→Act→Observe cycles, each cheap to verify, too tedious to want to do by hand.

Poor fit for the loop

A one-line config toggle you could type yourself in ten seconds; framing and verifying it costs more than just making the edit.

DECIDE STAGE

Before you start

  • Click the model badge at the bottom of the panel, or type /model, to bring up the model list
  • Fast tier for routine, formulaic steps; a stronger tier when framing or reasoning is the bottleneck.
  • Don't pick out of habit; the right tier depends on the task.
  • The bottom bar also shows an agent count: how many subagents are running in parallel right now.
  • The clock next to it counts down the prompt cache window — once it hits zero, the next message reprocesses the full conversation instead of reading from cache.
  • Cache reads cost ~10% of the standard input-token rate; writing to the cache carries a premium (~1.25x for the 5-minute window, ~2x for the 1-hour window) — paid once, then every re-read is the cheap 10%.

Decide Stage: Pick the Right Risk Posture

Same task, different mode, different operational risk.

Pick Your Mode

Why this matters before you pick

  • Your mode choice sets the speed vs. control tradeoff for every change in this task.
  • Plan mode lowers risk on ambiguous or high-impact changes by forcing review before execution.
  • Default (act) mode increases throughput on well-scoped tasks with known acceptance criteria.

ACT Stage

The one device you'll use all day: first by hand, then designed into something that runs without you.

The Five-Ingredient Frame

Outcome

The end state, not the keystrokes.

Scope

The concrete target and boundaries.

Verification

How "done" is checked: run it, don't eyeball it.

Deliverable

The reviewable artifact handed back.

Guardrails: What NOT to do, and when to stop and ask.

Write it, run it once

You write the frame by hand and drive Claude Code (or Copilot Chat) through one task, start to finish. This is Lab 1.

Design it in, it runs without you

You bake the same frame into a Skill you invoke on demand, or an agent that runs it autonomously. This is Lab 2 → Lab 4.

The Frame in Practice: Poor, Better, Best

Same task, reviewing open reconciliation exceptions, framed four ways.

Poor

"Fix the reconciliation exceptions in the Meridian account."

No scope, no verification, no deliverable; Claude has to guess what "fixed" means and how to prove it.

Poor

"Outcome: fix the fee bug. Scope: the fee module. Verification: run the tests. Deliverable: updated code. Guardrails: don't break anything."

Every ingredient is present but too vague to execute or check against: completeness isn't quality (Lab 1).

Better

"Investigate the 12 open exceptions in recon_meridian.csv and classify each as a timing break or a true break."

Scope is named. Still missing verification and a defined deliverable format.

Best

"Classify the 12 open exceptions in recon_meridian.csv as timing or true breaks. Verify each against the custodian feed. Deliver a triage table showing the reasoning per exception. Don't auto-clear anything flagged as a true break: escalate those."

All five ingredients present: outcome, scope, verification, deliverable, guardrails.

Observe Stage

Responsible AI & Human-in-the-Loop

Agent output is never treated as ground truth; state it before anyone touches a keyboard.

The agent reports back

A diff, a test result, a summary: always something you review, never something you rubber-stamp.

You verify independently

Run the tests yourself. Read the diff yourself. The scorer and the test suite are checklists, not judges of truth.

Check it against the frame

Verification isn't invented at review time; it's the method the task frame already named. Observe is where you hold the output to that bar.

The Loop, Powered by the Frame

Same four stages you just met, now with the frame attached. Claude Code is an agent that runs the loop on every task and the frame governs it at every step.

Read

Reads the relevant files and CLAUDE.md before touching anything.

→

Decide

Picks an approach against the frame's Outcome: the target it's aiming for.

→

Act

Edits within the frame's Scope: the boundary it isn't allowed to cross.

→

Observe

Checks its own work against Verification, then hands back the Deliverable.

→
Guardrails are different

Guardrails is a cross-cutting override that can interrupt any stage above (a risk threshold, a protected file). Not a gap in the loop; the thing that can override the loop.

A Small-Change Playbook

Turn the applied loop into three concrete choices before you touch a file.

1. Choose your mode

PlanUse it when the acceptance criteria or test shape is still unclear.
ActUse it for a bounded edit once the target is clear.

2. Choose your model

FastUse the cheaper model for routine checks and narrow steps.
StrongerUse the more capable model when framing or reasoning is the bottleneck.

3. Reference your skill

FrameName the skill explicitly so the workflow is visible and repeatable.
ReuseKeep the task narrow; let CLAUDE.md and .claude/skills/ carry the standard.

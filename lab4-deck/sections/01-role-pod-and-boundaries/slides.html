09:30 – 10:45 · Core Concept

What Is a Subagent, and Why Would You Need One?

A subagent (.claude/agents/*.md) runs in its own context: its own history, its own model, its own tool list, separate from your main session, and disposable. Once it reports back, that context is gone.

Independence

  • Never saw the reasoning behind the code.
  • Can't be talked into rubber-stamping a blind spot the same conversation would miss.

A disposable context

  • Its exploration happens in a context window thrown away once it reports back.
  • Only the verdict lands in your conversation.
  • Your main session's context budget stays exactly as it was.

Enforced restriction, not a suggestion

  • contract-reviewer's tools are locked to Read, Grep, Glob.
  • No Edit, no Bash.
  • It is not able to patch the code, no matter the main session's permission mode.
How you call one

No slash command, no special syntax. Plain English: "Use the <name> subagent to <do the task>." For example: "Use the contract-reviewer subagent to review the changes in reconcile.py."

09:30 – 10:45 · Skill vs. Subagent

Reach for a Subagent When Isolation Actually Buys You Something

Not every reusable workflow needs a subagent: a Skill is the cheaper default. This is a decision, not a reflex.

A Skill

  • Runs inline, in your main session: shares its context and history.
  • The cheap, default choice for a reusable workflow.
  • Fine when the workflow doesn't need independence from the conversation driving it.

A subagent

  • Runs in its own context, with its own enforced tool list and its own model, discarded once it reports back.
  • Earns its overhead when you need independence, a disposable context, or an enforced restriction your main session can't give itself.
  • Usually a reviewer or explorer, not an implementer.

09:30 – 10:45 · Core Concept

Why a Pod, Not One Conversation

A single conversation doing everything has three problems that better prompting doesn't fix.

It reviews its own work

It has a stake in the reasoning that produced the code, and will defend a shortcut it invented forty messages ago.

It carries everything

Reading six files to trace a dependency leaves six files in your context for the rest of the session, whether you need them or not.

It has every tool, always

"Please don't edit the fee tiers" is a request. A reviewer without Edit is a control.

The cost

A pod addresses all three by construction, but now you have to design the hand-offs. That's the actual skill this lab teaches.

09:30 – 10:45 · Core Concept

What Is a Subagent Pod?

A pod is a small set of named subagent roles, each an isolated .claude/agents/*.md definition with its own context, its own tool list, and one narrow job. You don't run them all yourself: you route the work and review the verdicts.

Named roles, not tasks

implementer, test-author, contract-reviewer: each one is reusable across tickets, not written fresh per task.

You staff, they execute

Your job shifts to deciding which role does a piece of work, in what order, and what each one hands the next.

One shared working tree

They don't get private copies of the repo. That makes the hand-off order a real design decision, not a formality.

09:30 – 10:45 · Core Concept

The Two Kinds of Boundary

The most important distinction in the lab. Every role's restriction is one of these two, and knowing which is the difference between a framework and a wish.

Tool-enforced

  • contract-reviewer's tools are Read, Grep, Glob. No Edit, no Write, no Bash.
  • It genuinely cannot edit your code. Bash matters most, since python3 -c "open(...).write(...)" is an edit too.
  • Holds regardless of the main session's permission mode, and regardless of what the role is asked to do.

Contract-only

  • implementer has Edit and is told "never edit a test file." test-author has Edit and is told "never edit source."
  • Neither is enforceable with a tools: list: it gates tool types, not file paths.
09:30 – 10:45 · The Three Shipped Roles

Read Them Before You Imitate Them

All three live in .claude/agents/. Each explains its own design decisions inline, and they're the templates for the fourth role, which is yours to write.

implementer

Read, Edit, Bash · contract-only. Makes a failing test pass, then verifies. Never edits a test file.

test-author

Read, Write, Edit, Bash · contract-only. Turns criteria into failing tests; repairs tests a change made untrue. Never edits source.

contract-reviewer

Read, Grep, Glob · tool-enforced. Reviews the finished diff against acceptance criteria, independently. Cannot patch anything.

The one that acts

implementer is the exception to "subagents are reviewers and explorers." Edit + Bash close a loop: change code, run tests, read the failure, change again, a cycle that would otherwise cost the main conversation a round trip per iteration.

09:30 – 10:45 · Watch the Hand-off

One Bug, Three Roles, One Seam Worth Noticing

implementer's fix for WM-106 makes the target test pass, and makes a different, previously-passing test false. Watch what happens next.

Step 1 · implementer

FixImplements the stock-split rule. Target test passes, a strategy-count test now fails.
ReportsFlags the broken test. Does not edit it: that's its contract.

Step 2 · test-author

RepairsUpdates the stale assertion: the test was right yesterday, wrong today, and nothing about the fix is at fault.

Step 3 · contract-reviewer

ReviewsIndependently checks the diff against the acceptance criteria. Verdict, not a vibe.
Why this is two roles, not one

An implementer with a red test has two ways to make it green: change the code, or change the test. The first is the job. The second is how a suite quietly stops meaning anything.

09:30 – 10:45 · The Hazard Nobody Warns You About

Subagents Share One Working Tree

They don't get private copies of the repo. Two roles holding Edit and running at the same time will overwrite each other, and the loser's work is gone with no error message.

The rule

Fan out reads and reviews. Serialize edits.

In this pod

Both implementer and test-author can Edit. That's not a bug; sometimes you genuinely need two editors across a session. You, not the model, are responsible for never having both live at once.

09:30 – 10:45 · Author the Fourth Role

reference-data-steward: Yours to Write

Read-only, tool-enforced. It answers one question about a diff: could the team who owns this data change it without an engineer and a release?

Tool budget

Needs Read and Grep. Must not have Edit, Write, MultiEdit, Bash, or Task.

Use the closest template

contract-reviewer is the closest shape: read-only, checklist-driven, returns a verdict.

Its full contract

09:30 – 10:45 · Knowledge Check

Quick Check: The Pod and Its Boundaries

1. Why is contract-reviewer called "tool-enforced" while implementer is called "contract-only"?

(a) contract-reviewer just runs on a stricter model.

(b) contract-reviewer's tools: list makes editing genuinely impossible; implementer's "never edit a test" is a prose instruction a tools: list can't express.

(c) They're the same thing, just different names.

2. implementer's fix breaks a previously-passing test. What should it do?

(a) Edit the test so the suite goes green again.

(b) Report the failure and leave the test alone; repairing a stale test is test-author's job.

(c) Delete the failing test.

3. Two roles both hold Edit. What's the safe way to run them?

(a) Run them at the same time to save turns.

(b) Fan out reads and reviews, but serialize edits: only one editor live on the shared working tree at a time.

(c) It doesn't matter; subagents get private copies of the repo.

4. Your new reference-data-steward role never gets picked when you describe a task without naming it. What's the most likely cause?

(a) Claude can't do proactive delegation at all.

(b) Its description says what the role is instead of when to reach for it.

(c) The role needs Bash to be selectable.

15:00 – 16:30 · Grounding the Lab

No New Ticket: Just Every Move You Know, Combined

Every subagent up to now ran against a fixture built for this course. This lab hands you two subagents and points them at a codebase nobody wrote for teaching purposes: yours, or the course repo as a fallback.

The problem

You know how to be handed a subagent (Lab 4), author one (Lab 5), and let a Skill delegate to one (Lab 7), but only ever against code built for the lab. Applying that judgment to real, messy code is a different skill than following a script.

The fix

Run codebase-mapper and pattern-scout in parallel, cross-reference what they find yourself, and produce a short, citation-backed recommendation: no ticket, no test file, just a codebase and a room of peers.

Your goal for Lab 8

Produce my-recommendation.md, every row backed by a citation, and present it to the room; expect at least one challenge.

15:00 – 16:30 · The Actual Point

The Synthesis Is Not Delegated: That's the Point

Two subagents produce two independent reports. Cross-referencing them into a judgment call is work only the main conversation does.

What the subagents do

codebase-mapper reports architecture, entry points, data flow, and hotspots. pattern-scout reports repetition signals (Skill candidates) and risk signals (Subagent candidates), as two separate lists. Neither one recommends anything.

What only you do

Cross-reference the two reports; a hotspot both flagged is a far stronger case than either signal alone, then apply the Lab 4/5 test to each candidate that survives: bounded and repeated (Skill), or does isolation / an enforced tool restriction / a different model actually earn its overhead here (Subagent)?

A third subagent doesn't do this step. Delegating the judgment call itself would defeat the lab's whole purpose.
15:00 – 16:30 · Why the Hook Matters More Here

Enforced Restriction, Now on Code You Don't Fully Control

Lab 7 introduced hooks. This is the first lab where the target might be a codebase you don't fully control the blast radius of yet, your team's, not a lab fixture.

Read tools aren't enough on their own

pattern-scout also needs Bash, to read git history: log, shortlog, blame. A permission mode alone can't tell git log from git push apart just by looking at the tool name.

The hook makes it enforced, not requested

validate-readonly-git.sh runs on every PreToolUse Bash call and blocks anything that isn't a read-only git history command, no matter what permission mode the session is running in.

Confirm it, don't assume it: the Definition of Done asks you to watch the hook visibly block at least one command during the session, even one you tried on purpose.
15:00 – 16:30 · The Verification

A Presentation Is a Legitimate Verifiable Target

Every earlier lab's Verification ingredient was something automated: a test file, a checker script, a fail-closed gate. This lab's is a person in the room.

When a script can verify

The acceptance criteria are objective and can be written down in code ahead of time: the fee tiers, the impact note's required call sites, a release gate's exit code.

When it can't

The deliverable is judgment about real, varied code: "is this actually repeated" or "does this risk really earn a subagent" are calls a peer who knows the codebase can challenge, and a script can't.

Verified by a short presentation, not a test file; expect at least one challenge, especially if you analyzed a codebase others in the room also touch.

codebase-mapper: One Job, Four Things to Report

Read-only, and deliberately doesn't recommend anything itself: that synthesis belongs to the main session, after it reads this report alongside pattern-scout's.

---
name: codebase-mapper
description: Maps a codebase's architecture: entry points, module
  boundaries, major data flows, and flags complexity hotspots.
  Read-only. Use when orienting in a codebase before recommending
  Skills or Subagents for it.
tools: Read, Grep, Glob
model: sonnet
---

## What to produce
1. Shape: top-level module/package layout, in a few lines
2. Entry points: where execution starts, cite file and function
3. Data flow: for the 2-3 most central objects, cite each hop
4. Complexity hotspots: name it, cite it, say why it qualifies
15:00 – 16:30 · Code Example

A Hook, Not a Suggestion

pattern-scout's Bash tool is real, because git-history inspection needs it; the hooks: block is what keeps it from being anything more than that.

.claude/agents/pattern-scout.md

---
name: pattern-scout
description: Finds repeated, hand-done workflows (Skill candidates),
  and high-risk or judgment-heavy code (Subagent candidates).
  Read-only, git-history-aware.
tools: Read, Grep, Glob, Bash
model: sonnet
hooks:
  PreToolUse:
    - matcher: "Bash"
      hooks:
        - type: command
          command: "./scripts/validate-readonly-git.sh"
---

15:00 – 16:30 · Knowledge Check

Quick Check: Put It All Together

1. Why run codebase-mapper and pattern-scout in parallel instead of one after the other?

(a) Parallel subagents always produce better reports

(b) Neither depends on the other's output; sequencing them wastes the point of delegating, the same reasoning as Lab 5's fan-out

(c) The hook requires them to run together

2. Who does the cross-referencing between the two subagents' reports?

(a) A third subagent, purpose-built for synthesis

(b) The human, in the main conversation: that synthesis is deliberately not delegated further

(c) Whichever subagent finishes first

3. codebase-mapper flags a hotspot that pattern-scout doesn't mention at all. Is it automatically a strong Skill/Subagent candidate?

(a) Yes: one subagent flagging it is enough

(b) No: overlap between the two reports is the stronger signal, and every candidate still has to pass the Lab 4/5 test on its own merits

(c) No: only pattern-scout's findings count toward the recommendation

4. Why is a presentation an acceptable verifiable target here, when every earlier lab used a test file or checker script?

(a) Presentations are easier to grade than code

(b) The deliverable is open-ended judgment about real, varied code: a defensible presentation that survives peer challenge is the honest substitute when no deterministic check can grade it

(c) This lab has no verifiable target at all
